# ANA 백준 수집과 점수 정산

## 확인한 데이터 원본

- [ANA 그룹 랭킹](https://acmicpc.net/group/ranklist/13872)은 로그인 없이 응답했다. 확인 당시 3페이지에 100·100·40행이 있었다. `#ranklist`의 아이디 링크 `/user/{handle}`에서 핸들을 읽는다. 맞은 문제와 제출 컬럼 모두 숫자 링크이며, 전체 제출 내역은 **제출** 컬럼의 링크에서 찾는다. 페이지 수는 화면 링크에서 읽고 고정하지 않는다.
- [백준 채점 현황](https://acmicpc.net/status)은 `#status-table`에 제출 번호, 아이디, 문제, 결과, 제출 시각을 표시한다. 시각은 `data-timestamp`의 Unix 초를 UTC로 변환한다. 확인한 두 페이지는 행이 각각 20개였고, 다음 페이지의 첫 제출 번호는 링크의 `top` 값과 같았다. 다음 요청은 마지막으로 찾은 AC 번호가 아니라 사이트가 준 **다음 페이지의 `top`**을 따른다.
- [robots.txt](https://acmicpc.net/robots.txt)는 일반 자동 크롤러의 `/status` 접근을 제외한다. ANA의 백준 읽기는 운영팀에서 허락받았다고 확인했으므로, 지원받은 그룹과 공개 제출 화면에 그 허용 범위를 적용한다.

## 백준 페이지 읽기 간격

- 백엔드에서 `BojPageReader` 인스턴스 하나가 그룹 랭킹, 회원별 첫 제출 페이지, 다음 제출 페이지를 모두 읽는다. 요청은 들어온 순서대로 한 번에 하나씩 처리하고, 직전 응답 본문을 다 읽거나 요청이 실패한 뒤 최소 **5초**를 기다린다. `429`와 `503`의 `Retry-After`가 더 길면 읽기 서비스 전체를 그 시간만큼 쉰다.
- 백엔드 프로세스가 5분 경계마다 수집을 시도한다. 240명의 제출 페이지를 모두 한 번씩만 열어도 20분 가까이 걸리므로, 변경 회원과 채점 대기 회원을 우선 처리하고 정기 대조는 여러 주기로 나눈다. MySQL 잠금으로 한 번에 백엔드 인스턴스 하나만 수집한다.

## 5분 수집 주기

1. 그룹 랭킹의 모든 페이지를 받고 핸들 기준으로 DB와 비교한다. 맞은 문제 수나 전체 제출 수가 달라진 회원, 이전 채점 대기 건이 남은 회원, 마지막 확인이 24시간 이상 지난 회원을 조회 대상으로 잡는다. 랭킹 조회가 일부만 성공하면 그 결과로 회원을 제외 처리하지 않는다.
2. 전체 제출 내역을 최신순으로 읽는다. 현재 `user.solution`에 저장된 값보다 큰 행만 후보로 모으고, 같은 번호 또는 그 이하를 만나거나 원본이 정상적으로 끝났다고 확인하면 멈춘다. 백준 제출 번호는 사용자별로 연속적이지 않다. 제출 번호 정렬, 요청한 회원, 다음 링크를 검증하고 403·429·로그인 화면·표 구조 변화는 정상적인 빈 페이지와 구분한다.
3. 후보를 오래된 순서로 처리한다. 최종 AC의 제출 번호와 원 제출 시각을 저장한다. 최종 오답도 조사 완료 커서는 전진시키지만 풀이로 저장하지 않는다. 부분 점수와 채점 대기 상태는 구분한다. 미확정 제출에 닿으면 그보다 최신인 행은 다음 실행에서 다시 읽는다. 중간 페이지가 실패하면 그 회원의 커밋을 보류한다.
4. 새 AC가 있으면 회원과 해당 문제의 티어를 solved.ac에서 조회한다. 이어서 회원별 쓰기 트랜잭션에서 예상 커서를 확인하고, 제출 번호 유일 제약과 정올과 공유하는 일일·이벤트 지급 키를 사용해 풀이·점수·현재 KST 월 점수 합계·커서를 함께 반영한다. 기존 회원의 누락분은 원 제출 시각으로 정산한다. 신규 회원은 첫 페이지에서 기준선을 잡고 주기마다 한 페이지씩 과거 해결 문제를 등록한 뒤 기준선 이후만 지급한다. 이벤트는 이벤트와 문제 등록 이후이면서 이벤트 기간의 해당 AC에 회원·이벤트·문제별로 한 번 지급한다. 순회가 끝나면 랭킹의 해결 수와 저장된 고유 해결 수의 차이를 `solved_count_delta`에 기록한다. 이미 커서를 지난 제출과 점수는 과거 기록으로 보존한다.

## 사용자 확인과 전체 과거 풀이

그룹 랭킹에서 처음 보는 아이디를 백엔드의 확인 후보로 등록한다. 재시작하면 다음 랭킹에서 후보를 다시 발견한다. Chromium 브라우저의 solved.ac 공개 프로필로 같은 백준 계정의 연결을 확인한다. 미등록 화면이면 회원 생성과 백준 제출 조회를 건너뛰고, 그룹에 계속 있는 아이디는 한 시간 뒤 다시 확인한다. 풀이가 0건이어도 백준 계정이 연결되어 있으면 다음 수집 주기에 등록한다. 일시적인 오류는 재시도한다. 신규 회원 확인에는 공식 API를 사용하지 않는다.

신규 회원을 처음 저장할 때 `user`에 solved.ac 핸들과 과거 풀이 진행 상태를 함께 기록한다. `011`에서 예약한 기존 회원의 과거 풀이 작업도 `012`에서 진행 중인 페이지와 재시도 시각을 그대로 옮긴다. 미평가 문제를 포함해 조회한다. 그룹의 제출 수가 양수인데 백준 채점 현황이 정상적인 빈 페이지를 반환하면 회원과 과거 풀이 작업을 먼저 등록하고, 백준 기준 제출 번호는 다음 주기에 다시 확인한다. [공식 v4 API](https://backstage.solved.ac/developer/docs)에서 `solved_by:아이디`를 ID 오름차순으로 50개씩 조회한다. 한 페이지를 적재하는 트랜잭션에서 다음 페이지 번호를 함께 저장한다. 응답 실패나 재시작 뒤에는 DB에 남은 페이지를 이어서 읽는다.

검색 결과에서 백준 원본 번호가 하나로 특정되는 문제를 저장한다. 서로 다른 원본을 합친 문제의 결과만으로는 회원이 어느 번호를 풀었는지 알 수 없다. 해당 문제는 채점 현황에서 확인한다. solved.ac에는 각 제출 번호와 시각이 없으므로 검색 결과는 기존 초기 풀이 형식으로 저장한다. 제출 커서, 일일 점수, 이벤트 점수는 채점 현황 경로에서 처리한다. 페이지에서 받은 제목과 티어는 해당 과거 풀이 기록에 저장한다.

공식 API를 쓰는 과거 풀이·신규 정답 정산에는 `SOLVED_AC_CLIENT_ID`와 `SOLVED_AC_CLIENT_SECRET`이 필요하다. 두 값이 없으면 신규 회원의 브라우저 확인은 계속하고, API가 필요한 풀이 적재와 정산을 보류한다. Docker 밖에서 실행할 경우 `CHROMIUM_PATH`로 Chromium 실행 파일을 지정할 수 있다. [앱 등록](https://backstage.solved.ac/developer/apps)

## solved.ac 요청 제한

- 새 정답의 회원 티어와 문제 티어는 매번 solved.ac 공식 API에서 조회한다. 같은 회원이 한 번의 정산에서 같은 문제를 여러 번 풀었다면 그 문제는 한 번 조회한다. `user.tier`와 `problem.problem_tier`는 표시 및 풀이 기록에 쓰며, `problem.level`은 두 티어의 차이를 기록한다.
- `SolvedAcCollector` 인스턴스 하나가 백엔드에서 solved.ac 브라우저 사용자 확인, 공식 API 과거 풀이, 신규 정답의 티어 조회를 담당한다. 브라우저와 API 요청을 합해 **직전 작업 종료 후 최소 2초, 분당 최대 30건**이다. 백준의 5초 간격은 별도로 적용한다. MySQL 잠금으로 백엔드가 여러 개 떠 있어도 동시에 한 건만 전송하고, `boj_tier_provider.next_at`에 예약과 요청 종료 시각을 반영한다. 신규 회원 확인과 과거 풀이 조회는 각각 프로세스당 30초마다 최대 한 건을 처리한다. 같은 회원의 과거 풀이 페이지 사이에도 최소 30초를 둔다.
- 429를 받으면 `Retry-After`에 따라 solved.ac 요청을 쉰다. 헤더가 없으면 API는 60초, 브라우저는 120초를 적용한다. 통신 오류나 5xx는 해당 작업을 재시도 시각 이후로 미룬다. 공식 API의 401·403은 운영 로그에 남기고 solved.ac 요청을 24시간 보류한다. 백준 랭킹과 채점 현황은 계속 읽을 수 있다.
- 회원 연결이나 문제 티어를 확인할 수 없으면 해당 회원의 풀이·점수·제출 커서를 함께 보류한다. 다음 주기에서 이전 커서부터 재시도한다. 이미 적재한 제출과 점수는 당시 값으로 보존한다.

## 이관과 실행

1. 기존 Python 수집이 종료된 시점의 `anabada`를 읽기 원본으로 둔다. Compose의 `database-migrator`가 백엔드 시작 전에 기존 `migrations/`의 미적용 SQL을 실행한다. 원본은 `boj_bada`와 같은 MySQL 서버에 있어야 한다. 원본이 없는 신규 환경에서는 `006`까지 적용하고 `007`부터 대기한다.
2. `006_create_boj_bada.sql`은 `boj_bada`를 만들고 `007_import_anabada.sql`은 사용자 ID, 제출 커서, 풀이, 점수, 이벤트를 가져온다. 적용 이력은 기존 `jungol_bada.migrations`에 기록한다. 원본과 대상의 행 수, 점수 합계, 커서, 이벤트 연결을 대조한다. 백준을 단독 확인할 때는 백엔드에서 `bun run dist/cli.js --boj-once`로 한 주기 실행할 수 있다.
3. 적용 이력에 `012`가 기록되면 백엔드가 백준 수집을 자동으로 시작한다. `012`는 과거 풀이 진행 상태를 `user`로 옮기고 사용이 끝난 테이블 4개를 제거한다. `DB_PASSWORD`는 기존 값을 사용한다. `010`에서 추가한 `problem.solved_ac_observed_at`에는 solved.ac에서 풀이를 처음 확인한 시각을 저장한다. 확인 시각과 같거나 더 이른 실제 백준 정답이 들어오면 관측 행을 실제 제출로 갱신해 최초 풀이 점수가 빠지는 일을 막는다. 이후 제출은 이미 풀었던 문제의 재풀이로 처리한다.

공개·관리 API와 백준 수집기는 같은 `boj_bada`를 사용한다. 관리 화면에서 등록한 이벤트와 문제를 수집기가 그대로 정산한다. 수집 후 기존 월간 가중치로 순위를 다시 계산하고, 순위가 바뀌면 등록된 활성 Discord 웹훅에 알린다. 운영에서는 이관 기록이 확인되어야 배포와 health check가 성공한다.

자동 테스트는 페이지 경계와 채점 대기·중간 실패를 재현한다. `sh backend/test/run-mysql.sh`는 운영과 동일 버전의 일회용 MySQL에서 레거시 이관, 회원별 롤백, 중복 제출과 이벤트 재지급 방지, 실시간 티어 조회와 제공자 제한을 확인한다.

`WEBHOOK_URL`을 설정하면 백준 수집의 파싱·적재 실패와 solved.ac 공식 API 접근 차단이 기존 백엔드 장애 웹훅으로 전달된다. 백준 `429`와 커서 변경 충돌은 로그에 남기고, solved.ac `429`는 DB에 다음 요청 시각을 기록한다. 이 경우에는 각 재시도 흐름을 따른다. 같은 오류 코드와 작업 ID는 전송 성공 후 30분, 실패 후 1분 동안 재전송을 억제한다. 순위 변경 알림은 등록된 순위 웹훅으로 따로 보낸다.

`sh backend/test/run-boj-e2e.sh`는 로컬 Docker에서 빈 MySQL에 마이그레이션을 적용한 뒤, 테스트 회원 한 명을 랭킹에서 발견해 사용자 상세 화면까지 확인한다. 백준과 solved.ac 응답은 로컬 테스트 서버가 제공하며, Chromium 프로필 확인, 백준 페이지 파서, 제출·점수 적재, 웹 API와 프론트 화면을 실행한다. 결과 화면은 `test-output/boj-e2e/one-member-profile.png`에 저장된다.
