# Collector 운영 동작

이 문서는 `dev`에서 구현한 collector 운영 동작과 관측 기준을 정리한다. 이 동작은
`main`에 반영·배포되기 전까지 운영 환경에는 적용되지 않는다.

## 실행 시점과 중복 방지

- 정상 시작은 KST 기준 매 10분 정각(`:00`, `:10`, `:20`, `:30`, `:40`, `:50`)을 다음
  실행 경계로 사용한다.
- 서비스가 그 경계 사이에 시작되면 다음 정각 경계까지 기다린다. 즉, 시작 즉시 수집하지
  않는다.
- 명시적인 `run-once` 실행만 즉시 한 cycle을 수행한다.
- 이전 cycle이 아직 끝나지 않았을 때 다음 정각이 와도 새 cycle을 시작하지 않는다. 종료 뒤
  다음 유효 경계에서 다시 판단하므로 cycle은 겹치지 않는다.

## 지연·장애 알림

- cycle이 20분 이상 완료되지 않으면 unhealthy 상태로 취급한다.
- `WEBHOOK_URL`이 설정된 경우 해당 지연에 대해 한 번만 알리고, 같은 지연 상태에서 반복
  알림을 보내지 않는다.
- 지연 알림 이후에도 collector는 기존 cycle의 완료와 이후 예정 cycle을 계속 처리한다.
- `WEBHOOK_URL`은 선택값이다. 값이 없으면 webhook 알림 기능만 비활성화되며, 수집과
  스케줄링은 계속 동작한다.

## 완료 기록의 의미

성공적으로 끝난 cycle은 시작·종료 시각(KST), 경과 시간, 실제로 새로 삽입한 AC 수,
중복 건수, 잔여 작업 여부를 기록한다.

- AC 수는 새로 저장된 accepted submission 수이며 점수나 지급 건수를 뜻하지 않는다.
- 중복은 이미 처리되어 다시 삽입하지 않은 submission을 뜻한다.
- `success_pending`은 후속 처리 여부를 나타내는 boolean 상태다. 이는 다음 cycle 또는
  재시도로 넘길 잔여 작업이 있는지를 뜻하며, pending 건수나 작업 수가 아니다.

DB 반영과 webhook 전송은 분리된 책임이다. DB의 `hook`은 추첨 보드 알림을 위한 데이터이고,
`WEBHOOK_URL`은 collector의 지연·실패·정상 완료 운영 알림을 위한 별도 endpoint다. 두
대상은 서로 자동으로 복사하거나 전송하지 않는다. DB 반영이 성공한 뒤 운영 webhook 전송이
실패해도 이미 반영된 수집 결과를 되돌리지 않으며, 운영 webhook의 선택적 비활성화도 DB
수집 결과에 영향을 주지 않는다.
