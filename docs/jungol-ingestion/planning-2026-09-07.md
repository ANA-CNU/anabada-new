# Jungol 수집·적재 전환 기획 (역사 기록)

> 2026-09-07의 기획과 POC 기록을 보존한 문서입니다. 아래의 모든 시도 저장, 5분 systemd timer, 미래 모델 제안은 현재 운영 계약이 아닙니다. 현재 AC-only 저장과 10분 컨테이너 내부 scheduler 및 배포 절차는 [운영 가이드](./README.md)를 따르세요.

상태: 컨테이너·DB POC 완료, 운영 설계 기획 중  
최종 수정: 2026-09-07  
대상 그룹: [JUNGOL ANA 그룹 #1125](https://jungol.co.kr/group/1125)

## 1. 목표

기존 Baekjoon/AOJ 중심 수집 경로를 Jungol 중심으로 교체한다.

최종적으로는 다음 상태를 목표로 한다.

- ANA 그룹의 구성원을 Jungol의 안정적인 숫자 account ID로 식별한다.
- 그룹 구성원의 **모든 채점 시도**를 제출 ID 기준으로 중복 없이 내부 DB에 저장한다.
- 정답 시도에서 최초 해결을 계산하고, 기존 일일 점수·이벤트 점수·랭킹 계산으로 연결한다.
- 같은 데이터를 여러 번 수집해도 결과가 달라지지 않는 멱등 적재를 보장한다.
- 로그인/Cloudflare 상태가 만료되거나 차단되면 조용히 잘못된 데이터를 쓰지 않고 동기화를 중단하고 알린다.

## 2. 2026-09-07 실제 화면에서 확인한 사실

로그인되어 있고 ANA 그룹에 가입된 브라우저에서 다음을 확인했다.

### 그룹 랭킹

`/group/1125/rank`는 다음 값을 제공한다.

- 그룹 구성원의 숫자 account ID가 포함된 계정 링크: `/account/{accountId}`
- 표시 핸들
- 푼 문제 수
- 틀린 문제 수
- 스트릭
- AC 레이팅

숫자 account ID는 핸들 변경과 무관한 외부 식별자로 사용할 수 있다.

### 계정 요약

`/account/{accountId}`는 다음을 제공한다.

- 가입일, 랭킹, 맞은 문제 수, 틀린 문제 수, 스트릭, AC 레이팅
- 해결한 문제의 문제 ID 목록
- 틀린 문제의 문제 ID 목록
- 사용자별 제출 현황 링크: `/account/{accountId}/submission`

### 사용자별 제출 현황

`/account/{accountId}/submission`은 다음 컬럼을 가진 제출 표를 제공한다.

- 제출 ID
- 제출자
- 문제 제목과 숫자 문제 ID
- 결과와 점수
- 실행 시간
- 메모리
- 코드 길이
- 언어
- 제출 시각
- 과거 내역을 불러오는 `더 불러오기` 버튼

표에는 정답뿐 아니라 오답, 시간 초과, 부분 점수와 `정답 0점` 같은 결과도 나타난다.

### 그룹 제출 현황

`/group/1125/submission` 경로가 존재하며, 로그아웃 브라우저에서는 “로그인이 필요하며 그룹에 가입해야 한다”는 화면을 반환했다. 따라서 그룹 전체 제출 피드를 사용할 경우 브라우저 세션과 그룹 멤버십이 필요하다.

### 인증과 접근성

- 로그인된 일반 브라우저에서는 그룹 랭킹과 사용자 제출 내역이 정상 렌더링됐다.
- 로그인하지 않은 브라우저에서도 일반 계정/전체 랭킹 일부는 보이지만, 그룹 제출 현황은 볼 수 없다.
- 일반 웹 fetch는 일부 Jungol 페이지에서 403을 받았지만 브라우저 렌더링은 성공했다.
- 2026-09-07 전용 수집 계정으로 숨김 Chromium 브라우저에서 아이디/비밀번호 로그인이 CAPTCHA 없이 성공했다.
- 로그인 직후 `/group/1125/submission`의 실제 제출 행을 읽을 수 있었고, 같은 브라우저 세션의 새 탭에서도 `/group/1125/rank` 인증 상태와 랭킹 행이 유지됐다.
- 인증 토큰을 JavaScript 저장소에서 직접 읽었다는 증거는 없다.
- 로그인 쿠키가 `HttpOnly`, `Secure`, `SameSite` 중 어떤 속성을 갖는지는 아직 확인하지 않았다.
- Linux ARM64 Docker 환경에서는 headless Chromium 로그인과 수집이 성공했다. 실제 운영 서버의 공인 IP에서는 동일 이미지를 다시 검증해야 한다.

따라서 POC는 쿠키 값을 애플리케이션 설정으로 복사하는 설계가 아니라, 브라우저가 쿠키와 사이트 상태를 직접 관리하는 persistent profile 방식을 사용한다. 로그인 UI 자동화는 가능성이 확인됐지만, 운영 Linux IP에서도 같은 결과가 나오는지는 별도 POC로 검증한다.

## 3. 채택한 랭킹 기반 트리거와 알려진 한계

이번 POC는 요청한 방법론을 그대로 채택했다.

1. `/group/1125/rank`에서 전체 구성원을 읽는다.
2. 숫자 account ID로 `jungol_bada.user`와 대조한다.
3. 신규 계정이거나 `rank.solved_count > user.corrects`인 계정만 worker queue에 넣는다.
4. worker는 `/account/{accountId}/submission`을 열고, `user.solution`에 저장된 마지막 제출 ID를 만날 때까지 과거 방향으로 읽는다.
5. 수집을 모두 마친 후 한 사용자 단위 DB transaction에서 attempt insert, 사용자 통계, cursor를 함께 commit한다.

이 방식에는 의도적으로 수용해야 하는 한계가 있다. 사용자가 오답만 새로 제출하면 푼 문제 수가 그대로이므로 그 실행 주기에는 worker가 생성되지 않는다. 이후 새 문제를 풀 때 함께 backfill되지만, 다시는 문제를 풀지 않으면 해당 오답은 누락될 수 있다.

예를 들어 사용자가 오답만 새로 제출하면 푼 문제 수는 그대로이므로 동기화가 실행되지 않는다. 이후에도 새 문제를 풀지 않으면 그 오답 시도는 영구적으로 누락된다.

운영 안정화 뒤 다음 안전망을 별도로 추가하는 것을 권장한다.

1. 매 주기 그룹 제출 현황을 최신 제출부터 읽는다.
2. 이미 저장한 마지막 Jungol 제출 ID를 만나면 중단한다.
3. 새 제출을 제출 ID 기준으로 멱등 upsert한다.
4. 그룹 랭킹은 구성원 목록, 계정 메타데이터, 푼 문제 수 정합성 검사에 사용한다.
5. 랭킹 수치와 DB 파생값이 다르면 사용자 계정 요약/제출 내역을 다시 훑어 누락을 복구한다.

그룹 제출 피드가 headless 환경에서 안정적으로 사용할 수 없을 때만 사용자별 제출 현황을 주기적으로 순회하는 대안을 사용한다.

## 4. 현재 저장소 상태

현재 수집 경로는 두 개가 혼재한다.

### Python Baekjoon 수집기

- `crawling/main.py`: 5분 간격 실행
- `crawling/info/group_rank.py`: Baekjoon 그룹 랭킹 HTML 파싱
- `crawling/info/user_info.py`: Baekjoon 사용자 해결/제출 HTML 파싱
- `crawling/score/solvedac.py`: 적재와 점수 계산
- 개발 compose에서는 crawler 서비스가 켜져 있지만 운영 compose에서는 주석 처리되어 있다.

### TypeScript AOJ 동기화기

- `backend/src/api/sync/aoj.service.ts`: AOJ 사용자·문제·제출 API 수집, 적재, 점수 계산
- `backend/src/index.ts`: `*/5 * * * *` 주기의 `aoj-sync` cron 등록
- 운영 backend에 포함되어 실행되는 경로다.

Jungol 전환에서는 두 경로를 동시에 유지하지 않는다. 하나의 authoritative ingestion 경로를 정하고 나머지는 비활성화 또는 제거 대상으로 명시해야 한다.

현재 자동화 테스트는 사실상 없다. 특히 수집 응답 파싱, 페이지네이션, 중복 적재, 최초 정답 판정, 점수 중복 지급을 보호하는 테스트가 없다.

## 5. `jungol_bada` POC 데이터 모델

기존 DB는 건드리지 않고 새 MySQL database `jungol_bada`를 만든다. 기존 테이블 이름과 주요 필드는 유지하되, Jungol 식별과 멱등 적재에 필요한 필드만 추가했다.

### `user`

- 기존 `name`, `corrects`, `submissions`, `solution`, `kr_name`, 외부 handle, `tier`, `ignored` 유지
- `jungol_account_id`: 핸들이 바뀌어도 유지되는 숫자 account ID, unique
- `solution`: 마지막으로 **성공적으로 commit한 Jungol submission ID**로 의미 고정
- `last_rank_seen_at`, `last_submission_synced_at`

### `problem`

- 기존 `name`, `problem`, `problem_tier`, `time`, `level`, `repeatation`, `verdict` 유지
- `user_id`: `user.id` FK
- `external_submission_id`: Jungol submission ID, unique
- `raw_result_text`, `score DECIMAL(10,6)`, `runtime_ms`, `memory_kb`, `code_length_bytes`, `language`
- `time_text`: 표시 시각/ISO 시각 보조 저장
- `grouped_extra_count`: DOM 진단용 필드. 실제 적재는 원본 attempt를 펼치므로 0

### `sync_run`

- 실행 시작/종료, 상태, 랭킹 인원, 변경 사용자 수, worker 수, 신규 attempt 수, 오류 코드

향후 점수 계산을 붙일 때는 아래의 정규화 모델로 확장한다.

### `source_account`

- `id`: 내부 PK
- `platform`: `jungol`
- `external_account_id`: Jungol 숫자 account ID
- `handle`: 현재 표시 핸들
- `group_id`: `1125`
- `observed_solved_count`
- `observed_wrong_problem_count`
- `ac_rating`
- `last_seen_submission_id`
- `last_rank_seen_at`, `last_submission_synced_at`
- 유니크 키: `(platform, external_account_id)`

### `submission_attempt`

- `id`: 내부 PK
- `platform`: `jungol`
- `external_submission_id`: Jungol 제출 ID
- `source_account_id`
- `problem_id`
- `raw_result_text`
- `verdict_code`: 내부 정규화 코드
- `score`
- `runtime_ms`
- `memory_kb`
- `code_length_bytes`
- `language`
- `submitted_at`
- `collected_at`
- 유니크 키: `(platform, external_submission_id)`

### 파생 데이터

- 최초 정답은 `submission_attempt`에서 사용자·문제별 가장 이른 accepted 시도로 계산한다.
- 점수 지급 기록은 원인이 된 `submission_attempt.id`를 참조하고, 일일/이벤트 규칙별 유니크 키를 둔다.
- 랭킹의 푼 문제 수는 수집 트리거가 아니라 파생값 검증에 사용한다.
- 기존 `problem` 테이블을 호환 계층으로 유지할지, 새 파생 테이블로 대체할지는 데이터 보존 정책 결정 후 확정한다.

## 6. 권장 POC

POC는 운영 적재 전에 별도 테스트 데이터와 낮은 호출 빈도로 실행한다.

### POC A: 인증 및 브라우저 실행 가능성

동일한 실행 이미지에서 다음 세 모드를 순서대로 검증한다.

1. `headless: true` + 새 프로필로 공개 페이지 로드
2. `headless: false` + persistent profile에서 관리자가 한 번 직접 로그인/그룹 접근
3. 동일 persistent profile을 `headless: true`로 다시 열어 `/group/1125/rank`와 `/group/1125/submission` 로드

성공 조건:

- 제목이 challenge 페이지가 아니다.
- 로그인·그룹 가입 필요 화면이 아니다.
- 랭킹 행과 제출 행이 실제 DOM에 존재한다.
- 재시작 후에도 세션이 유지된다.

실패 조건:

- 403/429
- CAPTCHA 또는 Cloudflare challenge
- 로그인/그룹 가입 필요 화면
- 세션 만료 뒤 빈 표를 정상 성공으로 오판

CAPTCHA를 자동으로 풀지 않는다. 실패 시 작업을 중단하고 수동 재인증을 요청한다.

### POC B: 페이지네이션과 증분 경계

- 그룹 제출 표의 최초 로드 행 수를 기록한다.
- `더 불러오기` 1회 전후의 제출 ID 집합을 비교한다.
- 동일 제출 ID가 행 안의 `+N` 표시와 어떤 관계인지 확인한다.
- 마지막 저장 제출 ID를 만났을 때 더 이상 과거 페이지를 읽지 않는지 검증한다.

### POC C: 정규화와 멱등 적재

- 정답, 오답, 시간 초과, 부분 점수, 정답 0점을 각각 fixture로 보존한다.
- 같은 fixture를 두 번 적재해 `submission_attempt` 행 수와 점수 지급 건수가 증가하지 않는지 검증한다.
- 제출 시각에 날짜가 생략되어 `오후 01:23`처럼 표시되는 경우 정확한 timestamp를 얻을 수 있는 API/DOM 속성을 확인한다.

### POC D: 그룹 랭킹 정합성

- 랭킹의 구성원 수와 `source_account` 활성 구성원 수를 비교한다.
- 계정 요약의 해결 문제 ID 집합과 accepted attempt의 distinct 문제 ID 집합을 비교한다.
- 불일치 시 사용자별 제출 페이지로 backfill하는 복구 경로를 검증한다.

## 7. 운영 안전장치

- 초기에는 동시 요청 1개, 최소 호출 간격, 지수 backoff를 사용한다.
- 403, 429, challenge, 세션 만료를 데이터 없음으로 취급하지 않는다.
- persistent profile 디렉터리는 전용 볼륨에 두고 DB 비밀번호와 분리한다.
- 쿠키 값, HTML 원문, 사용자 코드, 제출 소스 코드는 로그에 남기지 않는다.
- 한 사용자의 실패가 전체 동기화 트랜잭션을 오염시키지 않도록 run/account 단위 상태를 기록한다.
- `sync_run`에 시작/종료, 수집 행 수, 신규 행 수, 중복 수, 마지막 제출 ID, 실패 원인을 기록한다.
- Jungol 약관/robots 정책과 운영 허용 범위를 배포 전에 확인한다.
- 기존 데이터 마이그레이션과 되돌리기 절차를 먼저 준비한 뒤 scheduler를 전환한다.

## 8. 현재 확정된 항목과 다음 결정

1. 별도 Linux `jungol-collector` one-shot 컨테이너를 사용한다.
2. 기존 DB는 보존하고 신규 database `jungol_bada`에 적재한다.
3. 전용 계정 자동 로그인 + persistent browser profile + challenge 시 수동 복구를 사용한다.
4. 초기 worker 동시성은 2로 제한한다.
5. 사용자별 수집은 랭킹 신규/해결 수 증가를 trigger로 삼는다.
6. 다음 결정은 기존 점수·이벤트 projection을 언제 `jungol_bada` 위에 이식할지와 wrong-only 누락 안전망을 언제 추가할지다.

## 9. Linux 서버 자동화 권장안

### 9.1 배포 토폴로지

기존 API backend와 분리된 **one-shot `jungol-collector` 컨테이너**를 만들고, Linux `systemd timer`가 5분마다 실행하는 구성을 권장한다.

```text
systemd timer (5분)
  └─ systemd oneshot service
       └─ flock으로 전용 profile lock 획득
            └─ jungol-collector container
                 ├─ Node.js + pinned Playwright/Chromium
                 ├─ /run/secrets/jungol_username
                 ├─ /run/secrets/jungol_password
                 ├─ /var/lib/anabada/jungol-profile
                 └─ MySQL 내부 네트워크
```

one-shot 방식을 택하는 이유는 다음과 같다.

- 실행별 시작/성공/실패 경계가 명확하다.
- 같은 systemd service가 아직 실행 중이면 다음 timer가 중복 프로세스를 시작하지 않는다.
- 각 cycle 뒤 Chromium을 정상 종료하므로 장기 실행 브라우저의 메모리 누적과 stale page를 줄인다.
- CAPTCHA/challenge 상태를 실패 코드로 고정하고 hot restart loop 없이 운영자에게 넘기기 쉽다.
- 기존 Docker Compose 기반 DB/network를 그대로 사용할 수 있다.

브라우저 시작 비용이 문제가 될 정도로 구성원이 늘어나면 동일한 상태 머신을 가진 장기 실행 single-replica 서비스로 전환할 수 있다. 초기 POC와 현재 그룹 규모에는 one-shot 방식이 단순하다.

### 9.2 Playwright/Chromium 컨테이너

- Node.js LTS + Playwright Chromium을 사용한다.
- Playwright 패키지와 Docker/browser 이미지 버전을 정확히 고정한다.
- Ubuntu/Debian glibc 기반 이미지를 사용한다. Alpine/musl은 Playwright 공식 브라우저 지원 대상이 아니다.
- Chromium은 root가 아닌 전용 사용자로 실행한다.
- 운영에서 `--no-sandbox`를 사용하지 않는다.
- container init을 사용해 Chromium 자식 프로세스를 정상 회수한다.
- Chromium의 `/dev/shm` 부족을 피하도록 `ipc: host` 또는 충분한 shared memory를 제공한다.
- collector는 외부 포트를 열지 않고 Jungol HTTPS와 MySQL 내부 통신만 허용한다.

Playwright 공식 Docker 문서도 crawler에는 non-root 사용자와 seccomp profile을 권장하며, Chromium에는 init과 충분한 IPC를 권장한다: [Playwright Docker](https://playwright.dev/docs/docker).

### 9.3 credential과 profile

아이디와 비밀번호는 Git, `.env`, Dockerfile, compose `environment`, 명령행 인자, 로그에 넣지 않는다. Docker Compose secrets로 collector에만 `/run/secrets/*` 파일을 제공한다.

```yaml
services:
  jungol-collector:
    secrets:
      - jungol_username
      - jungol_password

secrets:
  jungol_username:
    file: /etc/anabada/secrets/jungol_username
  jungol_password:
    file: /etc/anabada/secrets/jungol_password
```

Docker는 민감값을 환경 변수 대신 서비스별 secret으로 제공할 것을 권장한다: [Docker Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/).

일반 Docker Compose의 file-backed secret은 host 파일을 bind mount하는 방식이므로, `/etc/anabada/secrets/*` 원본 파일 자체를 root 소유 `0600`으로 보호한다. Compose long syntax의 `uid`, `gid`, `mode` 값만 믿고 host 원본 권한을 느슨하게 두지 않는다.

현재 POC 자격 증명은 대화에 직접 공유됐으므로, 운영용으로 계속 사용할 경우 POC 완료 후 비밀번호를 교체하고 새 값은 서버 secret으로만 전달하는 것이 안전하다.

Playwright는 `chromium.launchPersistentContext(userDataDir)`로 전용 profile을 연다.

- profile 예시: `/var/lib/anabada/jungol-profile`
- collector UID만 읽고 쓸 수 있게 권한 제한
- 저장소 mount와 일반 관리자 Chrome profile 재사용 금지
- profile을 로그/HAR/일반 artifact 수집 대상에서 제외
- `flock`과 DB advisory lock으로 동시 실행 금지
- collector 종료 시 context를 정상 close해 쿠키·local storage를 flush

Playwright는 `userDataDir`에 쿠키와 local storage 등 세션 데이터를 보존하며 같은 디렉터리를 여러 브라우저가 동시에 사용할 수 없다고 명시한다: [Playwright `launchPersistentContext`](https://playwright.dev/docs/api/class-browsertype#browser-type-launch-persistent-context).

`storageState.json`만 별도로 저장하는 방법도 있지만, 이 파일은 계정 사칭에 쓰일 수 있는 민감한 쿠키와 상태를 포함할 수 있다. 초기에는 별도 파일을 배포하지 않고 persistent profile volume 자체를 보호한다. Playwright도 인증 상태 파일을 저장소에 커밋하지 말라고 경고한다: [Playwright Authentication](https://playwright.dev/docs/auth).

### 9.4 인증 상태 머신

```text
START
  │
  ▼
profile lock 획득
  ├─ 실패 → SKIPPED_OVERLAP, 외부 요청 없이 종료
  ▼
persistent Chromium 시작
  ▼
/group/1125/submission 접근
  ├─ ANA 그룹 + 제출 표 확인 → AUTHENTICATED
  ├─ 로그인 화면 → secret으로 자동 로그인 1회
  │      ├─ ANA 그룹 + 제출 표 확인 → AUTHENTICATED
  │      └─ 실패 → AUTH_REQUIRED, 알림 후 종료
  ├─ 403/429 → BLOCKED, backoff 기록 후 종료
  └─ CAPTCHA/Cloudflare challenge → MANUAL_RECOVERY_REQUIRED

AUTHENTICATED
  └─ 증분 수집 → DB commit → context close → lock 해제 → SUCCESS
```

HTTP 200이나 URL만으로 로그인 성공을 판단하지 않는다. 반드시 그룹명/번호, 그룹 내비게이션, 제출 테이블 헤더, 유효한 제출 ID 또는 명시적인 정상 빈 상태를 확인한다.

다음은 “데이터 없음”이 아니라 실패다.

- 로그인 또는 그룹 가입 필요 화면
- Cloudflare `Just a moment`/challenge
- CAPTCHA
- 403/429
- 예상 DOM이 없는 200 응답

자동 로그인은 실행당 한 번만 시도한다. 실패 후 반복 로그인하면 계정 잠금이나 차단을 유발할 수 있으므로 circuit breaker 상태를 저장하고 운영자 확인 전에는 로그인 재시도를 중단한다.

### 9.5 수집 cycle

1. 그룹 랭킹에서 account ID, handle, solved/wrong count, AC rating을 읽는다.
2. 신규 account ID 또는 `rank.solved > db.corrects`인 사용자만 bounded worker queue에 넣는다.
3. 사용자별 페이지가 실제로 사용한 `/api/submission?...` 응답을 Playwright network event로 받는다.
4. 요청의 `X-Fp`를 키로 응답을 반복 XOR 해제한 뒤 BSON을 역직렬화한다.
5. Jungol UI가 `+N`으로 접은 연속 동일 사용자·문제 제출을 원본 attempt 목록으로 복원한다.
6. DB의 마지막 확정 submission ID를 만날 때까지 `더 불러오기`를 반복한다.
7. 새 제출을 오래된 순으로 정렬한다.
8. 네트워크 수집이 전부 성공한 뒤 사용자 transaction을 시작한다.
9. `external_submission_id` unique key로 attempt를 insert하고 사용자 카운터와 `solution` cursor를 같은 transaction에서 commit한다.

첫 POC에서는 Playwright의 network event로 host, path, method, status, content-type만 관찰한다. 쿠키, Authorization, request body, 사용자 코드, 전체 response body는 로그에 남기지 않는다. 안정적인 first-party JSON 응답을 확인하면 DOM보다 그 응답을 정규화하되, 브라우저 context 밖으로 쿠키를 추출해 재현하지 않는다. Playwright는 request/response event와 `waitForResponse`를 공식 지원한다: [Playwright Network](https://playwright.dev/docs/network).

Jungol route 번들을 확인하고 실제 wire 목록과 대조한 결과, `+N`은 연속된 같은 사용자·같은 문제 제출을 화면에서 묶은 개수다. POC 대상은 DOM 10행이지만 원본 목록과 실제 외부 제출 ID는 20건이었다. 따라서 운영 수집기는 DOM 행을 attempt로 사용하지 않고 복호화된 BSON 목록을 사용한다. 이 프로토콜은 공개 문서화된 API가 아니므로 필드나 암호화 방식이 바뀌면 파서 드리프트로 실패 처리해야 한다.

### 9.6 systemd 실행 정책

- timer: 5분 간격
- service: `Type=oneshot`
- collector profile/account별 lock 파일 하나
- transient network/5xx만 제한된 지수 backoff
- auth/challenge/config 오류는 자동 연속 재시도 금지
- 실패 상태는 `sync_run`과 systemd exit code에 함께 기록
- manual recovery flag가 있으면 Jungol에 요청하지 않고 즉시 종료
- SIGTERM에서는 DB transaction rollback, browser context close, lock release

systemd timer의 monotonic interval과 실행 누락 처리 방식은 공식 문서에 정의되어 있다: [systemd.timer](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html).

### 9.7 수동 복구

CAPTCHA나 Cloudflare challenge는 자동 해결하지 않는다.

1. scheduled collector가 완전히 종료되어 profile lock이 해제됐는지 확인한다.
2. 동일 image/profile을 쓰는 별도 recovery command를 `headless: false`로 실행한다.
3. noVNC를 사용할 경우 외부에 공개하지 않고 loopback에만 bind한 뒤 SSH port-forward로 접근한다.
4. 운영자가 challenge 또는 로그인을 완료한다.
5. recovery browser를 정상 종료해 profile을 flush한다.
6. manual recovery flag를 해제하고 collector를 한 번 실행한다.

### 9.8 운영 상태와 알림

`sync_run`에 다음을 기록한다.

- 상태: `running`, `success`, `skipped_overlap`, `auth_required`, `blocked`, `manual_recovery_required`, `failed`
- 시작/종료 시각, 실행 시간
- 랭킹 행 수
- 읽은 제출 행 수, 신규/중복 attempt 수
- 최초/마지막 외부 제출 ID
- `더 불러오기` 횟수
- 민감정보가 제거된 오류 코드

즉시 알림이 필요한 조건은 자동 로그인 실패, CAPTCHA/challenge, 반복 403/429, 장시간 무성공, solved count 불일치, 제출 ID 정렬 위반, 필수 필드/파서 드리프트다.

### 9.9 Linux POC 합격 조건

실제 운영 Linux 서버에서 다음을 모두 통과해야 한다.

1. pinned Playwright Chromium이 non-root/sandbox 상태로 시작된다.
2. Docker secret에서 credential을 읽어 자동 로그인한다.
3. 로그인 후 그룹 제출 표의 실제 행을 읽는다.
4. 새 탭과 container 재시작 뒤에도 persistent profile 인증이 유지된다.
5. `headless: true`에서 rank/submission DOM이 동일하게 나타난다.
6. `더 불러오기` 전후의 제출 ID와 정확한 timestamp를 얻는다.
7. `+N` 표기가 의미하는 모든 실제 채점 시도를 복원한다.
8. 동일 fixture를 두 번 적재해 attempt·최초 정답·점수가 증가하지 않는다.
9. 로그인 만료와 challenge를 정상 빈 데이터로 commit하지 않는다.
10. 강제 종료 뒤 cursor 이전 데이터가 손실 없이 재수집된다.

첫 인증 POC는 [container-poc-2026-09-07.md](./container-poc-2026-09-07.md), 랭킹→worker→DB 통합 POC는 [rank-worker-db-poc-2026-09-07.md](./rank-worker-db-poc-2026-09-07.md)에 기록했다. 현재 Linux ARM64 headless container에서 자동 로그인, 그룹 account 12개, `+N` 원본 20건 복원, `jungol_bada` 적재, 무변경 skip, 해결 수 증가 감지, submission cursor 중단, 강제 DB 오류 rollback까지 성공했다. 운영 서버 IP, secret mount, host persistent profile, 실제 2페이지 이상 계정의 페이지네이션은 아직 남아 있다.
